UCX Communicator - Transport Routing & Logic
=============================================

Implementation notes for src/communicators/ucx/UcxCommunicator.{h,cpp}.

The communicator is built on the UCP STREAM API (not tag matching). Stream
was chosen because it matches the byte-oriented Read(n)/Write(n) contract
that the rest of GVirtuS (Buffer, Process::getstring) already assumes;
partial reads are looped with UCP_STREAM_RECV_FLAG_WAITALL.

UCX still picks the optimal transport per message internally: small
messages travel eager (1 copy, TCP/SHM/inline-RDMA), large messages flip
to rendezvous and ride RDMA zero-copy. The hand-off is gated by
UCX_RNDV_THRESH (default 8 KiB) and is invisible to the stream caller.


1. STARTUP / CONNECT / WIREUP
─────────────────────────────

Server (Serve / Accept)                  Client (Connect)
────────────────────────                  ────────────────

ucp_worker_create()                       ucp_worker_create()
ucp_listener_create(addr) ───►            ucp_ep_create(sockaddr,
   conn_handler stores                       err_mode=PEER,
   ucp_conn_request_h                        err_handler=epErrCb)
ucp_worker_create() (one per
   accepted ep)
ucp_ep_create(conn_req,
   err_mode=PEER,
   err_handler=epErrCb)
            │                                 │
            ▼                                 ▼
   wireupServer(ep):                  wireupClient(ep):
     send 'A'  ─────────────────────►   recv 'A'
     flush                               send 'R'  ───►
     recv 'R' ◄─────────────────────     flush
            │                                 │
            └────────► return to Process ◄────┘
                       loop / matrix_mul

Why a wireup handshake? UCX wireup messages are exchanged lazily on the
first transfer over a new endpoint. Without forcing them up front, the
first user-level Write of a large payload can stall waiting for wireup.
The 1-byte A/R + flush pair drains wireup before any plugin call lands
on the wire.

Why raise_memlock_limit? RDMA zero-copy requires the buffer be pinned.
The default per-process RLIMIT_MEMLOCK is often 64 KiB; without bumping
it, every transfer above that silently falls back to UCX bounce buffers
and throughput collapses. The standalone benchmark measured a 3.5×
recovery at 64 MiB after pinning.

Why err_mode=PEER + err_handler? If the peer dies mid-transfer, an
endpoint without error handling spins forever in ucp_worker_progress.
With epErrCb installed, the failure surfaces and the endpoint is marked
dead via mPeerClosed (see section 5).

4. PER-OPERATION COMPLETION (OpState)
─────────────────────────────────────

We deliberately do NOT use ucp_params_t.request_init / request_size. Each
Read/Write/Sync allocates a stack-local OpState and threads it through
the request_param_t via UCP_OP_ATTR_FIELD_USER_DATA:

    struct OpState {
        std::atomic<bool> complete;
        ucs_status_t      status;
        size_t            length;   // populated by stream_recv_cb
    };

    void *req = ucp_stream_send_nbx(ep, buf, len, &param);
    if (req == nullptr) {
        // immediate completion: callback NOT fired; OpState defaults OK
    } else if (UCS_PTR_IS_ERR(req)) {
        throw runtime_error(ucs_status_string(UCS_PTR_STATUS(req)));
    } else {
        while (!state.complete.load()) ucp_worker_progress(worker);
        ucp_request_free(req);
    }

Advantages over a per-request slab:
  - Immediate-completion path is trivially correct (no slab-init race).
  - Recv length captured per call without parsing the slab.
  - No global allocator pressure; OpState lives on the caller stack.


5. EOF / PEER-DISCONNECT SEMANTICS
──────────────────────────────────

The backend's Process::getstring loops:

    while (c->Read(&ch, 1) == 1) { ... }   // 0 == EOF

UcxCommunicator matches that contract:

  epErrCallback(self, ep, status):
      self->mPeerClosed.store(true)         // atomic
      LOG INFO "endpoint closed by peer: ..."

  Read(buf, size):
      if (mPeerClosed) return 0             // fast EOF
      try   { return stream_recv_all(...); }
      catch (std::exception &e) {
          mPeerClosed.store(true);
          LOG INFO "Read() EOF: ..."
          return 0;
      }

  Write(buf, size): same pattern.

Why: in the backend, each accepted client is handled in a std::thread
detached from Process. An uncaught exception there would call
std::terminate and kill the entire Process child, preventing future
client connections. Returning 0 lets execute()'s loop exit cleanly, the
thread joins, and Process loops back into Accept() ready for the next
client.


6. SHUTDOWN
───────────

  Sync()  : ucp_ep_flush_nbx + wait_op → all pending sends acked.
  Close() : ucp_ep_close_nbx with flags=0 (graceful, not FORCE)
            → poll ucp_request_check_status until !UCS_INPROGRESS.
            → ucp_listener_destroy, ucp_worker_destroy.
            → if mOwnsContext: ucp_cleanup.

  FORCE close was used in earlier drafts; replaced with graceful close
  because FORCE can drop the last in-flight bytes if the caller didn't
  call Sync() first.

    Tuning knobs (set via Makefile + etc/ucx/<host>.env):
      UCX_TLS=rc_verbs,tcp        RoCE v2 + TCP fallback (rc_x not
                                  available in the 1.20 build, use rc_verbs)
      UCX_NET_DEVICES=mlx5_0:1    pin ONE IB device; "all" can overflow
                                  the 64-ep-address blob on multi-NIC hosts
                                  ("invalid bandwidth 0.00" was this bug)
      UCX_IB_GID_INDEX=3          GID for the 24.24.24.x RoCE v2 subnet
      UCX_RNDV_THRESH=8192        eager↔rendezvous crossover

    Per-host profile autoload (top-level Makefile):
      hostname -s == es-dpu-01 → include etc/ucx/es-dpu-01.env
      hostname -s == es-dpu-02 → include etc/ucx/es-dpu-02.env
    The profile pins UCX_DEV, UCX_GID_IDX, UCX_TLS, HOST_IP, HOST_IP_PEER,
    HOST_NETDEV, UCX_PORT. The `ucx-config` target regenerates
    etc/properties_ucx.json (backend bind = HOST_IP) and
    examples/ucx_benchmark/properties_ucx.json (client dial = HOST_IP_PEER)
    from the active profile; it is a dependency of `run-gvirtus-backend-ucx`
    and `run-ucx-matrix-single`. Use etc/ucx/generate-profile.sh on a new
    node to scrape the right values automatically.

10. KEY DIFFERENCES FROM EARLIER DRAFTS
───────────────────────────────────────

This doc supersedes the original tag-matching design. Summary of moves:

  features:        TAG + STREAM → STREAM only
  Read/Write API:  ucp_tag_send/recv_nbx → ucp_stream_send/recv_nbx
                   (+ UCP_STREAM_RECV_FLAG_WAITALL)
  Completion:      request_init/size slab → stack OpState via USER_DATA
  Close:           UCP_EP_CLOSE_FLAG_FORCE → graceful (flags=0)
  Endpoints:       no error handling → UCP_ERR_HANDLING_MODE_PEER + cb
  Startup:         no handshake → 1-byte A/R wireup + flush
  Resources:       no rlimit bump → raise_memlock_limit() in Serve/Connect
  EOF:             threw on peer-close → returns 0 (mPeerClosed flag)
  Config:          hard-coded port/IP in JSON → per-host .env profile
                   auto-loaded by Makefile; ucx-config regenerates JSON
  UCX version:     apt libucx-dev 1.12 client vs source-built 1.20 backend
                   produced "invalid bandwidth 0.00" → benchmark image now
                   FROM aauce25/gvirtus-dev so both sides share UCX 1.20

Validation: examples/ucx_benchmark/data_copy_bench.cpp uses the same
patterns. Measured 3.5× improvement at 64 MiB after pre-pinning, ~9 GB/s
bidirectional on Mellanox BlueField-3 RoCE v2. End-to-end GVirtuS
cublasSgemm round-trip working over the new UcxCommunicator (see
examples/ucx_benchmark/frontend_matrix_only.sh + `make run-ucx-matrix-single`).
